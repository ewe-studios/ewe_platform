## Problem

LLM context windows are finite. Long-running sessions accumulate interactions that exceed token limits. The agent needs a structured way to remember important information across sessions without overwhelming the context window with raw message history.

## Decision

The Context API owns a **three-tier memory hierarchy** that progressively distills session information from raw observations to condensed reflections to permanent working facts.

```
┌──────────────────────────────────────────────────────┐
│                  Working Memory                       │
│  Permanent facts about user, session, preferences     │
│  Always included in context. Small, curated.          │
│  Updated by user interaction or smaller model scan.   │
├──────────────────────────────────────────────────────┤
│                  Reflection Memory                     │
│  Summarized observations — time-scoped condensations  │
│  Generated when observation memory exceeds threshold.  │
│  References observation scru128 IDs for fast lookup.  │
│  Always included in context (smaller than raw obs).   │
├──────────────────────────────────────────────────────┤
│                  Observation Memory                    │
│  Time-scoped details — what we're working on now      │
│  Structured assertions with timestamps and refs.      │
│  Has internal semantic recall via vector search.      │
│  Generated when recent interactions exceed threshold. │
├──────────────────────────────────────────────────────┤
│                  Raw Messages (audit trail)            │
│  Never compacted. Full history of all interactions.   │
│  Source of truth — everything else derives from here. │
└──────────────────────────────────────────────────────┘
```

### Tier 1: Working Memory

**Purpose:** Permanent, always-present facts about the user and session.

**Content:**
- User identity, preferences, working style
- Session goals, constraints, key decisions
- Facts the user explicitly asked to remember
- Small tool call result summaries that are important long-term

**Characteristics:**
- **Always included** in context assembly (fits within ~500 tokens)
- **Continuously updated** — outdated facts are removed, new facts are added
- **Pushed to message store** with `message_type: working_memory` for hydration on resume
- **Generated by:** User interaction OR smaller model scanning session messages

**Structure:**
```json
{
  "message_type": "working_memory",
  "facts": [
    {
      "fact": "User prefers Rust over Python for backend services",
      "asserted_at": "2026-06-11T10:30:00Z",
      "source_message_id": "scru128-...",
      "confidence": 0.95
    }
  ],
  "version": 3
}
```

### Tier 2: Observation Memory

**Purpose:** Time-scoped structured details about current work.

**Content:**
- What we're working on right now
- Where we left off
- What the user asked last
- Important tool call result summaries (not raw output)
- Unusual phrasing or details the user used (preserve verbatim)

**Characteristics:**
- **Generated when** recent session interactions exceed ~30k tokens (Mastra-inspired threshold)
- **Has semantic recall** — vector search over observation content
- **Structured format** — clear distinction between assertions and questions
- **Preserves timestamps** — when was something said/done
- **References** — links back to source message scru128 IDs
- **Pushed to message store** with `message_type: observation` for replay

**Generation Goals:**
- Use precise verbs
- Preserve unusual phrasing (don't normalize user's unique expressions)
- Maintain important details relevant to current work
- Distinguish assertions from questions
- Include timestamps and source references

**Structure:**
```json
{
  "message_type": "observation",
  "observations": [
    {
      "type": "assertion",
      "content": "User is debugging authentication flow in valtron task executor",
      "timestamp": "2026-06-11T10:30:00Z",
      "source_message_id": "scru128-...",
      "scope": "current_session"
    },
    {
      "type": "question",
      "content": "User asked whether TaskStatus::Ignore should replace blocking loops",
      "timestamp": "2026-06-11T10:35:00Z",
      "source_message_id": "scru128-..."
    }
  ],
  "token_count": 28500
}
```

### Tier 3: Reflection Memory

**Purpose:** Summarized condensation of observation memory — reducing large verbose memory to smaller, actionable summaries.

**Content:**
- Condensed versions of observations
- Organized by recency (recent observations retain more detail)
- Older observations aggressively summarized
- Combined/merged related observations
- References to observation scru128 IDs for fast lookup

**Characteristics:**
- **Generated when** observation memory exceeds ~40k tokens (Mastra-inspired threshold)
- **Replaces** the entire observation memory when generated — observation is reduced to reflections
- **Pushed to message store** with `message_type: reflection` for replay
- **Always included** in context (smaller than raw observations)
- **Optimized for retrieval** — includes scru128 ID references for fast message lookup

**Generation Goals:**
- Reorganize observation memory completely when generated
- Preserve dates/times when present
- Combine related items into single entries
- Condense older observations more aggressively
- Retain more details for recent observations
- Maintain reference links to source messages

**Structure:**
```json
{
  "message_type": "reflection",
  "reflections": [
    {
      "summary": "Session focused on valtron task executor debugging — identified TaskStatus::Ignore as replacement for blocking loops in iterator implementations",
      "time_range": {
        "from": "2026-06-11T10:00:00Z",
        "to": "2026-06-11T11:00:00Z"
      },
      "observation_refs": ["scru128-...", "scru128-..."],
      "importance": 0.8
    }
  ],
  "generated_at": "2026-06-11T11:05:00Z",
  "observation_token_count_before": 42000,
  "reflection_token_count_after": 3500
}
```

### Generation Triggers (Mastra-Inspired)

| Trigger | Threshold | Action |
|---------|-----------|--------|
| Observation generation | Recent interactions > 30k tokens | Generate observation memory using **memory model** (smaller, cheaper) |
| Reflection generation | Observation memory > 40k tokens | Generate reflections using **memory model**, replace observation memory |
| Working memory update | User explicitly requests OR smaller model detects new fact | Update working memory, push to message store |

The memory model is configured via `AgentConfig::memory_model` — typically a smaller model (e.g., Haiku) for cost efficiency. If no memory model is configured, the primary model is used.

### Context Assembly Order

When assembling context for an LLM call, the Context API includes information in this order:

1. **System prompt** (instructions, tool definitions)
2. **Working Memory** (always present, ~500 tokens)
3. **Reflection Memory** (summarized observations, ~3k-5k tokens)
4. **Recent raw messages** (last N messages, fills remaining context window)
5. **Semantically recalled messages** (vector search for relevant older messages)

Observation memory is **NOT** directly included in context — it has been condensed into reflections. The agent only sees reflections + working memory + recent messages.

### Rationale

**Why three tiers instead of one?**  
- Raw messages are too large for context windows in long sessions
- A single summarization layer loses too much detail
- Three tiers provide progressive distillation: facts → observations → reflections, each at the right level of abstraction

**Why push memory updates to the message store?**  
- Memory snapshots become part of the audit trail
- On session resume, the latest working/reflection memory is directly loadable
- No separate storage layer needed — messages are the single source of truth

**Why semantic recall on observation memory but not raw messages?**  
- Observations are already structured and distilled — searching over them is more precise
- Raw message search is also supported (via Message API), but observation search is faster and more relevant
- Both are available — the Context API owns both search capabilities

**Why replace observation memory entirely when generating reflections?**  
- Prevents unbounded growth of observation data
- Reflections are the "current state" of what was observed — older raw observations are no longer needed in context
- References to observation IDs allow recovery if needed (via message store replay)

## Alternatives Considered

### Single memory tier (just summarize everything)
- **Pros:** Simpler
- **Cons:** Loses the distinction between permanent facts (working memory), current work (observations), and historical summaries (reflections)
- **Rejected because:** Different memory types serve different purposes in context assembly

- **Pros:** Reduces storage size
- **Cons:** Destroys audit trail, breaks replayability
- **Rejected because:** Message store is append-only; context reduction is handled by memory hierarchy
