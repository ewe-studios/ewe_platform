# 029 — Signals return (getter, setter) tuples; two-way bindings via compile-time registered callbacks

**Date:** 2026-06-09  
**Status:** Resolved

### Decision

`ctx.signal()` returns a `(getter, setter)` tuple — not a single `Signal<T>` object. This frees components from needing structs and lets them be written as pure functions.

```rust
fn App(ctx: &Context) -> Html {
    let (name, set_name) = ctx.signal(String::new());
    let (count, set_count) = ctx.signal(0);

    html! {
        <div>
            <input primal:onchange={set_name} value={name.get()} />
            <p>Hello, {name.get()}</p>
            <button primal:onclick={move |_| set_count.update(|c| c + 1)}>
                Count: {count.get()}
            </button>
        </div>
    }
}
```

### How it works

**Runtime API:**
- `getter.get()` → reads current value (subscribes to dependency graph if called inside an effect/computed)
- `setter.update(fn)` → mutates in place, triggers stabilise
- `setter.set(value)` → replaces value, triggers stabilise

**Two-way bindings (DOM → WASM):**

When a user types in an input and the Rust side needs to know, the setter is registered as a callback at compile-time:

1. The `html!` macro detects `{set_name}` used as an event handler
2. Codegen assigns the setter a unique numeric ID (monotonically increasing per component)
3. The setter is registered with the WASM callback manager at compile time
4. The JS runtime receives a reference like `primal:setter(42)` — where `42` is the setter's unique ID
5. When the user interacts (types, clicks, changes), JS calls `invoke_callback(42, value)` → Rust setter executes → signal updates → effects re-run

**Server-bound actions:**

If a signal update needs to reach the server, the user makes it explicit:

```rust
fn App(ctx: &Context) -> Html {
    let (message, set_message) = ctx.signal(String::new());

    html! {
        <input primal:onchange={set_message} />
        <button primal:onclick={move |_| send_message(message.get()) }>
            Send
        </button>
    }
}
```

The runtime doesn't auto-sync signals to the server. The user explicitly calls a function that makes the request. This keeps the boundary clear: DOM ↔ WASM is automatic via effects/callbacks, WASM ↔ server is explicit via actions.

### Compile-time codegen

The macro generates a setter registry entry for each setter used in event handlers:

```rust
// Generated by html! macro (conceptual)
let set_name = ctx.register_setter(signal_id, setter_closure);
// set_name has methods: .get(), .update(fn), .set(value), .callback_id() -> u64
```

The setter carries:
- `id()` → the unique numeric identifier for cross-boundary communication
- `set(value)` → replace value
- `update(fn)` → mutate in place
- Internally: `Arc` reference to the signal's storage, registered callback

### Why this design

- **No string keys** — setters are identified by numeric IDs, not names (consistent with decision 011)
- **Component functions** — no need for structs, just `(getter, setter)` pairs in function scope
- **Compile-time registration** — all callback IDs are assigned at build time, no runtime string lookup
- **Explicit server boundary** — WASM ↔ DOM is automatic, WASM ↔ server is user-initiated
- **Leptos-inspired ergonomics** — familiar pattern for Rust UI developers
- **Type-safe** — compiler enforces setter types, no runtime casts or string parsing

### What this means for server patches

Since the server never sends string-keyed signal patches to the client, there's no mismatch with the Arc-based signal identity (decision 011). Server responses carry HTML (`primal-html`) or Arrow DOM ops (`primal-arrow`) — the DOM is updated directly, and any signal changes happen client-side as a result of those DOM updates or user actions.
