# 014 — `#[wasm_bin]` vs `#[wasm_worker]` vs `#[wasm_service]` — Execution Mode Design

**Date:** 2026-06-08
**Status:** Resolved

### Decision

Three proc macros control how the WASM binary communicates with the outside world. The WASM binary itself doesn't know which mode it runs in — it uses the same imported functions. The wrapper code (generated by the proc macro) handles the delivery mechanism.

---

## Message Envelope

Every message sent in either direction starts with a protocol header:

```
[protocol: u8][version: u8][payload_length: u32][payload...]
```

| Byte | Meaning |
|------|---------|
| `protocol` | 0 = custom binary (foundation_wasm Instructions), 1 = Arrow, 2 = JSON |
| `version` | Protocol version for backward compatibility |
| `payload_length` | Remaining bytes |
| `payload` | Protocol-specific data |

The WASM binary reads `protocol` and `version` from incoming messages and dispatches to the correct handler. It doesn't know or care how the message arrived.

---

## `#[wasm_bin]` — Main Thread (Direct)

### What it generates

```rust
// WASM binary side
#[wasm_export]
pub fn invoke(params_ptr: u32, params_len: u32, returns_ptr: u32) {
    // Reads protocol byte from params, dispatches to handler
}
```

```javascript
// Generated JS wrapper
const instance = await WebAssembly.instantiate(bytes, imports);
window.wasmExports = instance.exports;

function callWasm(protocol, payload) {
    const buffer = encodeEnvelope(protocol, 1, payload);
    const ptr = instance.exports.allocate(buffer.length);
    writeMemory(ptr, buffer);
    instance.exports.invoke(ptr, buffer.length, returnsPtr);
}
```

### Characteristics
- **Sync or async** — direct WASM function call
- **No serialization overhead** — shared memory
- **No transport** — `wasmExports.invoke(...)` directly
- **Single thread** — no postMessage, no HTTP

## `#[wasm_worker]` — Web Worker (postMessage)

### What it generates

```rust
// WASM binary side — same imports, same code
// Compiled into a worker-friendly WASM binary
```

```javascript
// Generated worker.js
importScripts('foundation-wasm.js');

const worker = new Worker(new URL('./worker-wrapper.js', import.meta.url));

function callWorker(protocol, payload) {
    const buffer = encodeEnvelope(protocol, 1, payload);
    worker.postMessage({ type: 'invoke', data: buffer }, [buffer.buffer]);
    // Response comes back via postMessage
}

// Worker side
self.onmessage = (e) => {
    if (e.data.type === 'invoke') {
        const result = wasm_invoke(e.data.data);
        self.postMessage({ type: 'result', data: result }, [result.buffer]);
    }
};
```

### Characteristics
- **Async only** — `postMessage` is inherently async
- **Serialized** — data copied to/from worker (Transferable mitigates this)
- **Isolated thread** — main thread stays responsive
- **Worker file** — can be `js=single-file` (bundled WASM as base64/Uint8Array) or separate `.wasm` fetch

### Delivery options

```rust
#[wasm_worker]                      // separate .wasm fetch
#[wasm_worker(js=single-file)]      // bundled JS with WASM
#[wasm_worker(js=single-file, encoded=b64)]    // base64 encoded
#[wasm_worker(js=single-file, encoded=uint8array)] // Uint8Array (default)
```

## `#[wasm_service]` — Service Worker (HTTP Interception)

### What it generates

```rust
#[wasm_service]
pub fn route(req: Request) -> Option<Response> {
    match req.path() {
        "/api/users" => Some(handle_users(req)),
        "/api/auth" => Some(handle_auth(req)),
        _ => None, // pass through to server
    }
}
```

```javascript
// Generated service-worker.js
importScripts('foundation-wasm.js');

self.addEventListener('fetch', (event) => {
    const route = wasm_route(event.request.url, event.request.method);
    if (route === 'handled') {
        event.respondWith(wasm_handle(event.request));
    }
    // else: pass through to server
});
```

### Characteristics
- **HTTP interface** — looks like a normal HTTP endpoint to the client
- **Intercepts fetch** — service worker catches matching routes, passes rest to server
- **Async** — fetch is async
- **Can work offline** — service worker serves cached responses
- **Single-file or separate** — same delivery options as `#[wasm_worker]`

### Delivery options

```rust
#[wasm_service]                     // separate .wasm fetch
#[wasm_service(js=single-file)]     // bundled JS with WASM
#[wasm_service(js=single-file, encoded=b64)]
#[wasm_service(js=single-file, encoded=uint8array)]
```

## Protocol Handler System

The WASM binary dispatches incoming messages based on the protocol byte:

```rust
// Inside foundation_wasm (shared across all modes)
fn dispatch_message(message: &[u8]) {
    let protocol = message[0];
    let version = message[1];
    let payload = &message[6..];  // skip protocol + version + length

    match protocol {
        0 => handle_custom_binary(payload, version),
        1 => handle_arrow(payload, version),
        2 => handle_json(payload, version),
        _ => panic!("unknown protocol"),
    }
}
```

The **same dispatch code** runs regardless of execution mode — the wrapper just delivers bytes differently.

---

## Component Awareness

Components and renderer code are **completely unaware** of the execution mode:

```rust
// Same code works in all three modes
fn render(&self, ctx: &Context) -> Html {
    let renderer = ctx.renderer();
    renderer.render(html! { ... });
}
```

When `renderer.render()` queues DOM ops, the underlying delivery (direct call, postMessage, or fetch) is handled by the proc macro wrapper. The component doesn't know and doesn't care.
