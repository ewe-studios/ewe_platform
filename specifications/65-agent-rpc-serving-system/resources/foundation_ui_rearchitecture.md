# Ewe Platform: High-Performance Cross-Platform SDUI Architecture Specification
*System Architecture Review, Wire Protocol Optimization, and Stateless Behavioral Contracts*

---

## 1. Executive Summary & Core Design Philosophy

The Ewe Platform architecture is an ultra-fast, zero-copy framework designed to deliver **Server-Driven User Interfaces (SDUI)** and **State synchronization** seamlessly across Web, iOS, and Android. It avoids common multi-platform performance pitfalls—such as thick Virtual DOM runtimes, complex hydration loops, and text-heavy parsers (JSON/HTML)—by employing a strictly compile-time macro layout engine, pre-compiled native CPU bindings, and a universal binary serialization tier.

### Core Superpowers
- **No Virtual DOM or Client-Side Layout Diffing:** Every dynamic interaction targets precise, compile-time registered elements directly.
- **Unified Network Contract:** A single, consistent FlatBuffer outer container manages all over-the-wire communication across Web, Mobile, and Desktop platforms.
- **Zero Client-Side Cache Churn:** View states ride directly on layout elements as pre-signed, cryptographically secure binary properties, eliminating state tracking map overhead entirely.
- **Multi-Tier Performance Optimization:** Supports lightning-fast primitive modifications via FlatBuffers, direct array-buffer casting via custom 8-byte aligned Columnar blocks, and vectorized mass data pushes powered by Apache Arrow IPC streams.

## 2. The Unified Wire Protocol: FlatBuffers Wrapper Framework

To enforce type-safety and allow painless schema evolution without breaking legacy client installations, the network layer utilizes **FlatBuffers as the Universal Outer Envelope Container**. It wraps around specialized binary formats using an explicit native `union` mapping structure.

### Universal Schema Specification (`foundation_wire_protocol.fbs`)

```flatbuffers
namespace ewe.platform;

// 1. Explicit data payload containers isolating raw byte structures
table ColumnarPayload {
  // Pre-aligned 8-byte layout matrix for direct JS zero-copy casting
  data: [ubyte];
}

table ArrowPayload {
  // High-volume tabular metric streams (Apache Arrow IPC streams)
  data: [ubyte];
}

table MessagePackPayload {
  // Complex unstructured objects, dynamic maps, or schema-less states
  data: [ubyte];
}

// 2. Explicit structural tables for native mobile SDUI mutations
enum HtmlTagId : ushort { UNKNOWN = 0, DIV = 1, SPAN = 2, INPUT = 3, BUTTON = 4 }
enum AttrNameId : ushort { UNKNOWN = 0, CLASS = 1, ID = 2, STYLE = 3, VALUE = 4 }

table CreateElementOp { node_id: uint; tag_id: HtmlTagId; custom_tag_name: string; class_name: string; }
table SetTextOp       { node_id: uint; text_value: string; }
table SetAttributeOp  { node_id: uint; attr_id: AttrNameId; custom_attr_name: string; value: string; }
table AppendChildOp   { parent_id: uint; child_id: uint; }

union DomOperation {
  CreateElement: CreateElementOp,
  SetText: SetTextOp,
  SetAttribute: SetAttributeOp,
  AppendChild: AppendChildOp
}

table DomOpRow {
  op: DomOperation;
}

table MobileLayoutPayload {
  // Explicit semantic layout mutations stream for mobile native view builders
  ops: [DomOpRow];
}

// 3. Define the Core Union that explicitly selects the active pipeline
union PayloadData {
  Columnar: ColumnarPayload,
  Arrow: ArrowPayload,
  MessagePack: MessagePackPayload,
  MobileLayout: MobileLayoutPayload
}

// 4. The Universal Outbound Wire Envelope
table WireEnvelope {
  version: ushort = 1;
  sequence_id: uint;
  payload: PayloadData;
}

// 5. The Universal Inbound Action Request Envelope
table FlatBufferState {
  flatbuffer_blob: [ubyte];
  binary_schema: [ubyte]; // Optional self-description (.bfbs content)
}

union StateFormatPayload {
  Integer: long,
  Float: double,
  Text: string,
  Json: string,
  MessagePack: MessagePackPayload,
  Arrow: ArrowPayload,
  FlatBuffer: FlatBufferState,
  CustomBinary: [ubyte]
}

table InlineNodeState {
  format: StateFormatPayload;
  security_hmac: [ubyte]; // Cryptographic token signature generated by server
}

table UserInteractionRequest {
  version: ushort = 1;
  sequence_id: uint;
  node_id: uint;
  event_name: string;
  active_state: InlineNodeState;
  input_value: string;
}

root_type WireEnvelope;
```

## 3. Platform Execution Matrix

### Web Browser Client Optimization (FFI Zero-Copy Loop)
When a network frame arrives in the browser containing `PayloadData::Columnar`, it bypasses the WebAssembly runtime execution thread for UI rendering:
1. The lightweight JavaScript applicator reads the outer FlatBuffer container layout instantly with minimal offset computing overhead.
2. It extracts the raw memory address pointer location of the nested `columnar_raw` byte vector.
3. It performs a **zero-copy typed array cast** directly over the network buffer chunk:
   ```javascript
   const uint32View = new Uint32Array(rawBytes.buffer, rawBytes.byteOffset, rawBytes.byteLength / 4);
   ```
4. It iterates over raw numeric slots to blast mutations straight to the DOM with zero object allocation or structural parsing churn.

### Mobile Engine Integration (iOS & Android)
Mobile apps completely drop standard web view wrappers, JavaScript execution dependencies, or remote bytecode runtimes (avoiding App Store Guideline 2.5.2 restrictions).
- **The Core Architecture:** The framework's core runtime logic (`foundation_signals`, `foundation_ui_components`) is compiled directly into the application package as a native machine-code binary target (`aarch64`) via **UniFFI** or static C-bindings.
- **The Render Pipeline:** When the native client processes a `PayloadData::MobileLayout` FlatBuffer, it uses fast CPU memory offsets to loop through the explicitly typed `ops` array. It translates abstract primitives directly to native declarative views (SwiftUI on iOS, Jetpack Compose on Android) synchronously at native machine execution speeds.

## 4. Stateless Behavior: Element-Riding Binary States

To achieve massive, horizontal system scalability and avoid fragile client-side cache stores, view states ride directly on the UI element instances as secure, tamper-proof properties.

### The Security Lifecyle
1. **The Server-Side Generation:** When a view component template compiles, the backend processes the parameters into binary blocks, generates a **HMAC-SHA256** authentication tag using a rotating master secret, and packages them as element properties.
2. **The Interaction Interception:** When a user taps a native mobile node or clicks a browser DOM item, the runtime automatically harvests the `data-state` and `data-state-token` values right from that specific element object. It wraps them into the `UserInteractionRequest` network payload without intermediate parsing.
3. **The Stateless Execution:** The incoming frame can land on any server replica. The replica instantly matches the cryptographic signature using pointer calculations. If validated, it rehydrates the model context, runs the transaction logic, updates the values, and immediately clears the memory context.

## 5. Server-Side Actions Model: The `#[action]` Macro Engine

The framework employs a macro-driven, type-directed routing paradigm. By decorating backend handler functions with the `#[foundation_ui::action]` procedural attribute, developers can write atomic transactional boundaries that automatically parse network parameters and drive outbound wire streams smoothly based on function signature bounds.

```rust
use std::uuid::Uuid;
use serde::Serialize;
use foundation_wasm_ui::Context; // True framework context core
use foundation_ui_traits::DomOp;

#[derive(Serialize)]
pub struct Counter {
    pub counter_id: Uuid,
    pub current: i32,
}

pub struct Interaction<T> {
    pub node_id: u32,
    pub event_name: String,
    pub input_value: String,
    pub state: T,
}

pub enum Response {
    UIUpdate(Vec<DomOp>), // Automatically translates to Columnar/MobileLayout FlatBuffers
    DataUpdate(Vec<u8>),  // Transmits raw Arrow, MessagePack, or custom binary signals
}

// ==========================================
// EXPLICIT ACTION ENGINE IMPLEMENTATION
// ==========================================
#[foundation_ui::action]
pub fn increment_counter_ui(ctx: &Context, event: Interaction<Counter>) -> Response {
    // 1. Process isolated business logic
    let next_count = event.state.current + 1;
    
    let next_state = Counter {
        counter_id: event.state.counter_id,
        current: next_count,
    };

    // 2. The html! macro evaluates right here!
    // It detects the `Some(&next_state)` parameter bound to serde::Serialize.
    // It code-generates the required layout operations, converts `next_state` to MessagePack, 
    // signs it via HMAC, and embeds `data-state` and `data-state-token` automatically.
    let computed_ops: Vec<DomOp> = html! { ctx, Some(&next_state),
        <button class="btn-primary" primal:onclick="increment_counter">
            "Count: " { next_count }
        </button>
    };

    // 3. Return the compiled operation list directly to the dispatcher pipeline
    Response::UIUpdate(computed_ops)
}
```

## 6. App Store & Ecosystem Compliance Strategy

Deploying dynamic user interfaces to consumer mobile hardware introduces stringent marketplace constraints, particularly regarding **Apple App Store Review Guideline 2.5.2** (Executable Code). The Ewe platform satisfies these rules out of the box through a defensive structural segregation design:

- **Data-Driven Configuration Models:** FlatBuffers transmits standard, declarative structural data configurations (`UiOperation` structures and layout layout tokens) rather than raw dynamic scripts, imperative execution parameters, or runtime binary bytecode.
- **Pre-Compiled Element Primitives:** All base UI elements (your 8 primitive layout families including buttons, text cells, and inputs) remain fully compiled as native machine code inside the application binary package distributed by the App Store. The server payload simply arranges or updates variables over these pre-existing targets.
- **The Declarative Command Bus:** Instead of passing uncompiled functional closure references across a remote network boundary, events map to unique string identifiers (e.g., `"primal:onclick" -> "increment_counter"`). The mobile app validates this token string against a local static registry of pre-compiled actions, executing on-device functions securely without invoking runtime interpretation or risky script environments.
