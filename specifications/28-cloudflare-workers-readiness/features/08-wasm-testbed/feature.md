# Feature: Foundation WASM Testbed

## Overview

A CLI crate `foundation_wasm_testbed` that provides a unified testing interface for wasm32-unknown-unknown projects. It replaces the complexity of `wasm-pack test` and `wasm-bindgen-test-runner` with a simple, predictable model:

- The CLI builds, stages files into the integration directory, then runs the test.
- The test runner (browser or Deno) loads everything via relative paths — no special endpoints, no scanning, no proxying.
- `bindgen-*` modes auto-generate harnesses from `#[wasm_bindgen_test]` macros.
- `web` and `deno` modes use user-provided JS in `integrations/{type}/`.

## Architecture

### Directory Structure

```
my_crate/
├── Cargo.toml
├── src/
│   └── lib.rs
└── integrations/
    ├── web/                          # User-provided browser tests
    │   ├── index.html                # Browser harness (scaffolded by init)
    │   ├── index.js                  # User test entry point (scaffolded by init)
    │   ├── loader.js                 # Wasm instantiation helper (editable)
    │   └── (user adds any .js, .css, mocks, helpers)
    ├── deno/                         # User-provided Deno tests
    │   ├── index.js                  # User test entry point (scaffolded by init)
    │   ├── loader.js                 # Wasm instantiation helper for Deno (editable)
    │   └── (user adds any .js helpers)
    ├── bindgen-web/                  # Auto-managed, never edited by user
    │   ├── index.html                # Generated at test time
    │   ├── {crate_name}.js           # Generated by wasm-bindgen
    │   ├── {crate_name}_bg.wasm      # Generated by wasm-bindgen
    │   └── run.js                    # Generated at test time (cx.run)
    └── bindgen-deno/                 # Auto-managed, never edited by user
        ├── {crate_name}.js           # Generated by wasm-bindgen (--deno)
        ├── {crate_name}_bg.wasm      # Generated by wasm-bindgen
        └── run.js                    # Generated at test time (cx.run)
    ├── wrangler/                     # User-provided Cloudflare Workers tests
    │   ├── worker.js                 # User test entry point (scaffolded by init)
    │   ├── loader.js                 # Wasm instantiation helper for Workers (editable)
    │   ├── wrangler.toml             # Wrangler configuration (editable)
    │   └── (user adds any .js, bindings, mocks)
    ├── bindgen-wrangler/             # Auto-managed, never edited by user
        ├── {crate_name}.js           # Generated by wasm-bindgen (ES modules)
        ├── {crate_name}_bg.wasm      # Generated by wasm-bindgen
        ├── worker.js                 # Generated test worker entry point
        └── wrangler.toml             # Generated minimal wrangler config
```

### CLI Commands

```
wasm-testbed init [TYPE] <crate_path>    # Scaffold integration directories
wasm-testbed test <MODE> <crate_path>    # Build, stage, and run tests
```

#### `init` Subcommands

| Command | Creates | Purpose |
|---------|---------|---------|
| `wasm-testbed init web ./my_crate` | `integrations/web/` with templates | Browser test scaffolding |
| `wasm-testbed init deno ./my_crate` | `integrations/deno/` with templates | Deno test scaffolding |
| `wasm-testbed init wrangler ./my_crate` | `integrations/wrangler/` with templates | Cloudflare Workers test scaffolding |
| `wasm-testbed init ./my_crate` | All six subdirectories | Full scaffolding |

#### `test` Subcommands

| Command | Runner | Harness |
|---------|--------|---------|
| `wasm-testbed test web ./my_crate` | Playwright (Chrome/Firefox/Safari) | User's `integrations/web/index.js` |
| `wasm-testbed test deno ./my_crate` | Deno | User's `integrations/deno/index.js` |
| `wasm-testbed test wrangler ./my_crate` | wrangler dev + curl | User's `integrations/wrangler/worker.js` |
| `wasm-testbed test bindgen-web ./my_crate` | Playwright (Chrome/Firefox/Safari) | Auto-generated from `#[wasm_bindgen_test]` |
| `wasm-testbed test bindgen-deno ./my_crate` | Deno | Auto-generated from `#[wasm_bindgen_test]` |
| `wasm-testbed test bindgen-wrangler ./my_crate` | wrangler dev + curl | Auto-generated from `#[wasm_bindgen_test]` |

## Test Mode Flows

### `test web <crate_path>`

```
1. Read Cargo.toml to get package name and profile (debug/release)
2. cargo build --target wasm32-unknown-unknown [--release]
3. Copy target/wasm32-unknown-unknown/{debug,release}/{name}.wasm
   → integrations/web/{name}.wasm
4. Start foundation_http server serving integrations/web/
5. Launch browser via Playwright → http://localhost:{port}/index.html
6. Poll until test results appear in a known DOM element or console pattern
7. Print results, clean up
```

### `test deno <crate_path>`

```
1. Read Cargo.toml to get package name and profile
2. cargo build --target wasm32-unknown-unknown [--release]
3. Copy target/wasm32-unknown-unknown/{debug,release}/{name}.wasm
   → integrations/deno/{name}.wasm
4. deno run --allow-read --allow-net integrations/deno/index.js
5. Print results
```

### `test bindgen-web <crate_path>`

```
1. Read Cargo.toml to get package name and profile
2. cargo build --target wasm32-unknown-unknown [--release]
3. wasm-bindgen target/.../{name}.wasm --out-dir integrations/bindgen-web/
4. Discover test exports by scanning wasm for __wbgt_ functions
   (use walrus to parse wasm binary, same as wasm-bindgen-test-runner)
5. Generate run.js that:
   - imports wasm-bindgen JS glue
   - creates WasmBindgenTestContext
   - calls cx.run(discovered_test_names)
6. Generate index.html that imports run.js
7. Start foundation_http server serving integrations/bindgen-web/
8. Launch browser via Playwright
9. Poll for results, print, clean up
```

### `test bindgen-deno <crate_path>`

```
1. Read Cargo.toml to get package name and profile
2. cargo build --target wasm32-unknown-unknown [--release]
3. wasm-bindgen target/.../{name}.wasm --out-dir integrations/bindgen-deno/ --deno
4. Discover test exports (__wbgt_ functions in wasm)
5. Generate run.js that imports wasm-bindgen output and calls cx.run()
6. deno run --allow-read --allow-net integrations/bindgen-deno/run.js
7. Print results
```

### `test wrangler <crate_path>`

```
1. Read Cargo.toml to get package name and profile
2. cargo build --target wasm32-unknown-unknown [--release]
3. Copy target/wasm32-unknown-unknown/{debug,release}/{name}.wasm
   → integrations/wrangler/{name}.wasm
4. Start `wrangler dev --port {random}` from integrations/wrangler/
5. curl http://localhost:{port}/ — worker loads wasm, runs tests, returns results
6. Print results, kill wrangler process
```

The user's `worker.js` is a standard Cloudflare Worker that exports a `fetch` handler. It loads the wasm module, runs whatever test logic the user writes, and returns the result as the HTTP response body. This tests the wasm in the actual Workers runtime (`ServiceWorkerGlobalScope`), not a browser or Deno approximation.

### `test bindgen-wrangler <crate_path>`

```
1. Read Cargo.toml to get package name and profile
2. cargo build --target wasm32-unknown-unknown [--release]
3. wasm-bindgen target/.../{name}.wasm --out-dir integrations/bindgen-wrangler/ --target esmodules
4. Discover test exports (__wbgt_ functions in wasm)
5. Generate worker.js that:
   - imports wasm-bindgen ES module output
   - exports fetch handler
   - on request, creates WasmBindgenTestContext, runs tests
   - returns test results as JSON/text response
6. Generate wrangler.toml with minimal config
7. Start `wrangler dev --port {random}` from integrations/bindgen-wrangler/
8. curl http://localhost:{port}/ — runs tests via wasm-bindgen context
9. Print results, kill wrangler process
```

No browser, no Deno — this tests in the actual Cloudflare Workers runtime environment via `wrangler dev` (local Workers simulator).

## Template Files

Templates are embedded at compile time via `foundation_macros::EmbedDirectoryAs`. The macro reads files from disk in debug mode (fast iteration) and embeds bytes directly in the binary for release builds.

Usage pattern:

```rust
use foundation_macros::EmbedDirectoryAs;

#[derive(EmbedDirectoryAs)]
#[source = "$ROOT_CRATE/integrations/foundation-wasm-testbed/src/templates/web"]
pub struct WebTemplates;

// Access individual files:
let html = WebTemplates.read_utf8_for("index.html");
let js = WebTemplates.read_utf8_for("index.js");
```

The `init` command reads the embedded templates and writes them to the target crate's `integrations/` directory, replacing `PACKAGE_NAME` placeholders with the actual crate name.

## Cloudflare Workers Integration

### Browser Selection

```
wasm-testbed test web ./my_crate --browser chrome    # default
wasm-testbed test web ./my_crate --browser firefox
wasm-testbed test web ./my_crate --browser safari
wasm-testbed test web ./my_crate --browser all        # run in all available
```

### Driver Management

Simplified from wasm-pack's approach:

| Driver | Management | Source |
|--------|-----------|--------|
| chromedriver | Auto-download if not on PATH | Google chrome-for-testing API |
| geckodriver | Auto-download if not on PATH | GitHub releases |
| safaridriver | PATH only (bundled with macOS) | System |

Unlike wasm-pack, we use Playwright to manage the browser session instead of raw WebDriver protocol. Playwright is invoked as a subprocess or via its Node.js API.

### Playwright Integration

Playwright replaces the hand-rolled WebDriver HTTP client from `wasm-bindgen-test-runner/headless.rs`. Flow:

```
1. CLI starts foundation_http on a random available port
2. CLI writes a small Playwright script to a temp file:
   - Launches browser (--headless if flag set)
   - Navigates to http://localhost:{port}/
   - Polls #output element for "test result: "
   - Prints element text, exits with appropriate code
3. CLI runs: npx playwright test (or node playwright-script.js)
4. Browser runs tests, results appear in #output
5. Playwright script scrapes and exits
6. CLI kills HTTP server
```

This avoids implementing the WebDriver protocol in Rust and leverages Playwright's mature browser management.

## HTTP Server

The `foundation_http` server serves via the `EmbedDirectoryAs` structs from `foundation_macros`. This provides a critical dev benefit: in debug mode, `read_utf8_for` reads from disk on every request, so the browser always sees the latest file content — templates, user JS, copied wasm binary — without recompiling the testbed. In release mode, files are served from embedded bytes.

The server serves a single directory: the target integration subdirectory. For example:

- `test web` → serves `integrations/web/`
- `test bindgen-web` → serves `integrations/bindgen-web/`

The CLI copies the wasm binary into the integration directory before starting the server, so all paths are relative — no special endpoints, no proxying, no scanning.

Server features needed:
- Serve files from an `EmbedDirectoryAs` struct (reads disk in debug, embedded bytes in release)
- Bind to a random available port
- Report the bound port back to the CLI
- Set appropriate Content-Type headers for .wasm (application/wasm)
- CORS headers (for same-origin, minimal)

## Testing Strategy

### Test the Testbed Itself

```bash
# Unit tests
cargo test -p foundation_wasm_testbed

# Integration test: build a fake wasm crate and test each mode
cargo test -p foundation_wasm_testbed --test integration
```

The integration tests use a minimal wasm crate that exports a test function, then verify that `wasm-testbed test deno` runs and reports success.

### Test User Crates

Users run the testbed against their own wasm crates:

```bash
# Basic web mode with custom harness
wasm-testbed test web ./backends/foundation_auth

# Browser tests with wasm-bindgen test macros
wasm-testbed test bindgen-web ./backends/foundation_auth --features wasm,wasm-bindgen-oauth --headless

# Deno tests
wasm-testbed test deno ./some-wasm-crate

# Deno tests with wasm-bindgen
wasm-testbed test bindgen-deno ./some-wasm-crate

# Workers tests with custom harness
wasm-testbed test wrangler ./backends/foundation_auth

# Workers tests with wasm-bindgen
wasm-testbed test bindgen-wrangler ./backends/foundation_auth --features wasm,wasm-bindgen-oauth
```

## Design Decisions

### Why not raw WebDriver in Rust?
The WebDriver protocol is verbose and browser-specific. Playwright has already solved cross-browser management, headless mode, and element scraping. We invoke it as a subprocess instead of reimplementing the protocol.

### Why copy wasm into integration directory instead of proxying?
No special server endpoints. The server serves one directory with static files only. Simpler to reason about, easier to debug (open the URL in any browser, see exactly what's served).

### Why keep loader.js as an editable file?
Users may need to customize imports (memory size, host functions, mock functions). Having it as a file they can edit is clearer than flags or configuration.

### Why separate web and bindgen-web?
`web` mode gives full control — users write their own test harness, mock functions, and assertions. `bindgen-web` is the fast path for standard `#[wasm_bindgen_test]` tests with zero user JS.

### Why include wrangler mode?
Browser and Deno environments approximate but don't replicate the Cloudflare Workers runtime. Workers run in `ServiceWorkerGlobalScope` (no `window`, no DOM), have unique bindings (KV, D1, R2), and different fetch behavior. Testing in `wrangler dev` catches runtime-specific issues that browser/Deno tests miss. This is the mode that validates the primary deployment target for spec 28.
