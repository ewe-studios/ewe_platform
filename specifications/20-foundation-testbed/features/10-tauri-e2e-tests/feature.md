# Tauri E2E Tests Feature

## Overview

Integration tests (in the `tests/` directory) that exercise the full VM lifecycle using a real Tauri application as the workload. Each test launches a VM, verifies SSH/WinRM connectivity, builds a minimal Tauri project inside the guest, launches the resulting binary for headless validation, and confirms the VM can be cleanly stopped. Tests are marked `#[ignore]` because they require a running KVM hypervisor, pre-built VM images, and several minutes of execution time.

## Dependencies

- Depends on **features 00 through 09** — all foundational pieces must be in place:
  - **00-host-bootstrap**: rust, mise, nushell, cargo-binstall, tauri-cli installed in VM
  - **01-qemu-backend**: VM launch, shutdown, disk management, snapshots
  - **02-vm-communication**: SSH (Linux guests) and WinRM (Windows guests) connectivity
  - **03-bootstrap-build-pipeline**: build orchestration inside VMs
  - **04-runner-utilities**: command execution, log capture, error extraction
  - **05-cli-state-management**: VM state tracking
  - **06-bin-integration**: CLI subcommand wiring
  - **08-provider-architecture**: provider abstraction (QEMU, UTM)
  - **09-project-mount**: host directory mounted at `/mnt/project` inside VM
- macOS deferred — no test for the UTM/macOS provider until feature 07 is complete

## Requirements

### 10.1 Test Infrastructure

- Integration tests live in `backends/foundation_testbed/tests/e2e_tauri.rs`
- All test functions carry `#[ignore]` attribute — run only with `--ignored`
- Each test follows the pattern: setup VM, execute steps, assert outcomes, tear down
- Tests must be idempotent: running the same test twice produces the same result without manual cleanup
- Tests share a common test fixture module (`tests/common/mod.rs`) that provides:
  - `TestVm` — RAII guard that starts a VM on construction and stops it on drop
  - `ensure_image()` — downloads/prepares the qcow2 image if missing
  - `tauri_example_dir()` — clones or returns the path to the Tauri example project
  - `assert_build_ok()` — validates build exit code and artifact existence
  - `assert_app_runs()` — validates the binary launches without immediate crash

### 10.2 Tauri Example Project

The tests use the **official Tauri quickstart app** generated by `cargo tauri init` / `npm create tauri-app`:

- **Source**: A minimal project created by `npm create tauri-app@latest tauri-e2e-test -- --template vanilla` or the equivalent `cargo tauri init` flow
- **Location**: Cloned to a temporary directory, or fetched from a known minimal repo
- **Contents**: A simple Tauri app with vanilla HTML/JS frontend (no framework dependencies that could introduce flakiness)
- **Bootstrap**: The test ensures `tauri-cli` is installed in the VM via the host bootstrap pipeline (feature 00)
- **Alternative**: If cloning from a remote is unreliable, the test creates the project inline by writing the minimal `Cargo.toml`, `src/main.rs`, `tauri.conf.json`, and `index.html` files directly

The minimal inline project structure:

```
tauri-e2e-test/
├── Cargo.toml              # [package] name = "tauri-e2e-test", [dependencies] tauri
├── src/
│   └── main.rs             # tauri::Builder::default().run(tauri::generate_context!())
├── tauri.conf.json         # Minimal Tauri config (bundle identifier, frontend dev path)
├── build.rs                # fn main() { tauri_build::build() }
├── index.html              # <html><body><h1>E2E Test</h1></body></html>
└── (package.json if using npm template)
```

### 10.3 Test: VM Lifecycle (All Platforms)

Verifies the complete VM start-run-stop cycle:

1. **Start**: Launch the VM (Windows or Linux) via `foundation_testbed::start()`
2. **Wait for connectivity**: Poll SSH (Linux, port 2222) or WinRM (Windows, port 5985) until reachable, with 5-minute timeout
3. **Verify reachability**: Execute `echo hello` via SSH/WinRM and confirm response
4. **Stop**: Gracefully shut down the VM via `foundation_testbed::stop()`
5. **Verify stopped**: Confirm QEMU process has exited and PID is gone

### 10.4 Test: Project Mount Verification

Verifies the host directory is accessible inside the VM:

1. Start VM with mount configured
2. Execute `ls /mnt/project` via SSH/WinRM
3. Assert exit code 0 and that expected files/directories are listed
4. Execute `touch /mnt/project/.mount-test && test -f .mount-test` on host side
5. Clean up test file

### 10.5 Test: Tauri Build — Linux Guest

Full build pipeline for `x86_64-unknown-linux-gnu`:

1. Start Linux VM with project mounted at `/mnt/project`
2. Wait for SSH connectivity
3. Clone or create the Tauri example project at `/mnt/project/tauri-e2e-test/`
4. Inside VM, run:
   ```bash
   cd /mnt/project/tauri-e2e-test
   cargo tauri build --target x86_64-unknown-linux-gnu
   ```
5. Assert build exits with code 0
6. Assert artifact exists on host at:
   ```
   $PWD/.testbed/artifacts/linux/tauri-e2e-test
   ```
   (or the equivalent path under `target/x86_64-unknown-linux-gnu/release/`)
7. Assert the artifact is a valid ELF binary (`file` command or magic bytes check)
8. Stop VM

### 10.6 Test: Tauri Build — Windows Guest

Full build pipeline for `x86_64-pc-windows-msvc`:

1. Start Windows VM with project mounted at `/mnt/project`
2. Wait for WinRM connectivity
3. Clone or create the Tauri example project at `C:\Users\vagrant\project\tauri-e2e-test\` (or the Windows equivalent of `/mnt/project`)
4. Inside VM, run:
   ```powershell
   cd C:\Users\vagrant\project\tauri-e2e-test
   cargo tauri build --target x86_64-pc-windows-msvc
   ```
5. Assert build exits with code 0
6. Assert artifact exists on host at:
   ```
   $PWD/.testbed/artifacts/windows/tauri-e2e-test.exe
   ```
   (or the equivalent path under `target/x86_64-pc-windows-msvc/release/`)
7. Assert the artifact is a valid PE binary (magic bytes `MZ`)
8. Stop VM

### 10.7 Test: Headless App Launch — Linux Guest

Validates the built binary can launch without crashing:

1. After a successful Linux build (test 10.5), launch the binary inside the VM:
   ```bash
   # Start Xvfb virtual display so GUI apps have an X server
   export DISPLAY=:99
   Xvfb :99 -screen 0 1024x768x24 &
   sleep 1

   # Launch the Tauri app
   /mnt/project/tauri-e2e-test/target/x86_64-unknown-linux-gnu/release/tauri-e2e-test &
   APP_PID=$!
   sleep 5

   # Check it is still running
   kill -0 $APP_PID
   ```
2. Assert the process is alive after 5 seconds (exit code 0 from `kill -0`)
3. Assert no crash output appeared in stderr within the first 5 seconds
4. Kill the app process
5. Xvfb is started as a **startup script** (feature 09 startup scripts) so it is available before the test runs, not started ad-hoc inside the test

### 10.8 Test: Headless App Launch — Windows Guest

Validates the built binary can launch without crashing:

1. After a successful Windows build (test 10.6), launch the binary inside the VM:
   ```powershell
   Start-Process -FilePath "C:\Users\vagrant\project\tauri-e2e-test\target\x86_64-pc-windows-msvc\release\tauri-e2e-test.exe" -WindowStyle Hidden
   Start-Sleep -Seconds 5
   $proc = Get-Process "tauri-e2e-test" -ErrorAction SilentlyContinue
   if ($null -eq $proc) { exit 1 }
   ```
2. Assert the process exists and is running after 5 seconds
3. Assert no Windows error dialog appeared (check Event Log for application crash entries in the last 30 seconds)
4. Kill the app process

### 10.9 Test: Full E2E — Linux

End-to-end test combining all steps in a single test function:

1. Start Linux VM
2. Verify SSH reachable
3. Verify `/mnt/project` mount accessible
4. Build Tauri project
5. Launch binary headlessly (Xvfb)
6. Verify app runs for 5 seconds without crash
7. Stop VM
8. Assert build log exists at `$PWD/.testbed/logs/linux-build.log`
9. Assert artifact exists on host

### 10.10 Test: Full E2E — Windows

End-to-end test combining all steps in a single test function:

1. Start Windows VM
2. Verify WinRM reachable
3. Verify project mount accessible
4. Build Tauri project
5. Launch binary headlessly
6. Verify app runs for 5 seconds without crash
7. Stop VM
8. Assert build log exists at `$PWD/.testbed/logs/windows-build.log`
9. Assert artifact exists on host

## Xvfb Virtual Display (Linux Headless GUI)

For Linux guests, GUI applications (including Tauri apps) require an X server. The test suite uses **Xvfb** (X Virtual Framebuffer) to provide a headless display:

### Setup

Xvfb is installed during the VM bootstrap (feature 00) as part of the idempotent package installation step:

```bash
# In bootstrap script (Linux guest)
sudo apt-get install -y xvfb || sudo pacman -S --noconfirm xorg-server-xvfb || true
```

### Configuration

A startup script (feature 09) launches Xvfb before any test runs:

```bash
# $PWD/.testbed/scripts/linux-build/startup/00-xvfb.sh
export DISPLAY=:99
if ! xdpyinfo -display :99 >/dev/null 2>&1; then
  Xvfb :99 -screen 0 1024x768x24 -ac &
  sleep 1
fi
```

### Test Usage

Tests set `DISPLAY=:99` before launching any GUI binary. The display number `:99` is chosen to avoid conflicts with any real X server that might be running on the host or VM desktop.

### Test Module Structure

### TestVm RAII Guard

The `TestVm` struct in `tests/common/mod.rs` ensures cleanup even on test panic:

```rust
/// RAII guard: starts a VM on creation, stops it on drop.
pub struct TestVm {
    profile: VmProfile,
    display: DisplayMode,
    started: bool,
}

impl TestVm {
    pub fn new(profile: VmProfile, display: DisplayMode) -> Result<Self> {
        let vm = Self { profile, display, started: false };
        // start VM, wait for connectivity
        Ok(vm)
    }

    pub fn ssh_exec(&self, cmd: &str) -> Result<ExecOutput> { ... }
    pub fn winrm_exec(&self, cmd: &str) -> Result<ExecOutput> { ... }
    pub fn wait_for_ready(&self, timeout: Duration) -> Result<()> { ... }
}

impl Drop for TestVm {
    fn drop(&mut self) {
        if self.started {
            // Always attempt graceful shutdown, even if test panicked
            let _ = foundation_testbed::stop(&self.profile);
        }
    }
}
```

### Test Execution Strategy

Tests use `#[serial]` (from the `serial_test` crate) to prevent multiple VMs from running simultaneously, which could cause port conflicts or resource exhaustion:

```rust
#[test]
#[ignore]
#[serial(linux_vm)]
fn test_full_e2e_linux() -> Result<()> {
    let vm = TestVm::new(VmProfile::linux_build(), DisplayMode::Headless)?;
    // ... test steps
    Ok(())
}

#[test]
#[ignore]
#[serial(windows_vm)]
fn test_full_e2e_windows() -> Result<()> {
    let vm = TestVm::new(VmProfile::windows_build(), DisplayMode::Headless)?;
    // ... test steps
    Ok(())
}
```

The `#[serial(linux_vm)]` and `#[serial(windows_vm)]` groups allow one Linux VM and one Windows VM to run tests in parallel with each other, but not two Linux VMs simultaneously.

### Tauri Example Project — Inline Creation

Rather than depending on network availability, the test creates the minimal Tauri project inline:

```rust
/// Creates a minimal Tauri project at the given directory.
/// No network access required.
pub fn create_tauri_project(dir: &Path) -> Result<()> {
    std::fs::create_dir_all(dir.join("src"))?;

    // Cargo.toml
    std::fs::write(dir.join("Cargo.toml"), r#"
[package]
name = "tauri-e2e-test"
version = "0.1.0"
edition = "2021"

[dependencies]
tauri = { version = "2" }

[build-dependencies]
tauri-build = { version = "2" }
"#)?;

    // build.rs
    std::fs::write(dir.join("build.rs"), "fn main() { tauri_build::build() }")?;

    // src/main.rs
    std::fs::write(dir.join("src/main.rs"), r#"
#![cfg_attr(not(debug_assertions), windows_subsystem = "windows")]

fn main() {
    tauri::Builder::default()
        .run(tauri::generate_context!())
        .expect("failed to run tauri app");
}
"#)?;

    // tauri.conf.json (v2 format)
    std::fs::write(dir.join("tauri.conf.json"), r#"
{
  "productName": "tauri-e2e-test",
  "version": "0.1.0",
  "identifier": "com.testbed.e2e",
  "build": {
    "frontendDist": "../dist"
  },
  "app": {
    "withGlobalTauri": false
  },
  "bundle": {}
}
"#)?;

    // dist/index.html (minimal frontend)
    std::fs::create_dir_all(dir.join("dist"))?;
    std::fs::write(dir.join("dist/index.html"), r#"
<!DOCTYPE html>
<html>
<head><title>E2E Test</title></head>
<body><h1>Tauri E2E Test App</h1></body>
</html>
"#)?;

    Ok(())
}
```

This approach has several advantages:
- **No network dependency** — tests work offline once images are cached
- **Deterministic** — same project every time, no upstream changes
- **Fast** — no `git clone` or `npm create` step
- **Controllable** — we know exactly what the project contains
