# Feature 22: Workspace, process and CI

_Written in ASD-STE100 Simplified Technical English (STE). Code and identifiers stay as they
are._

**Abbreviations in this file.** continuous integration (CI); WebAssembly (wasm); JavaScript (JS);
Hypertext Transfer Protocol (HTTP); pull request (PR); AeroSpace and Defence Industries
Association of Europe (ASD), the owner of the STE standard ASD-STE100.

Use the shared protocol in [`requirements.md`](../../requirements.md) sections 3 and 4. One
commit per entry. E3 (the crate split) is large: do it in its own PR after the others, and say so.

## T0. Check that every entry is still open (table in the PR body)

## E1. Parallel worktrees clobber one shared target directory

- **Problem:** with one `CARGO_TARGET_DIR` for many worktrees, `foundation_core` and
  `foundation_macros` build with the same hashes and overwrite each other's test binaries and
  proc-macro files mid-run (stale results, `E0460` doctest failures).
- **Fix:** `scripts/ci/ci.py` (and any worktree helper or mise task that sets the target
  directory) uses a target directory per worktree: `<repo>/target` by default, or
  `$CARGO_TARGET_DIR/<worktree-name>` when the variable is set. Document it in `.agents/`
  where worktrees are described. Do not use `-Cmetadata` (it rebuilds every dependency).
- **Verify:** two worktrees run `ci.py run foundation_core` at the same time; both pass; the
  printed target directories differ.

## E2. `crates/ewe_deployables` does not build

- **Problem:** not a workspace member; it uses the old sync `Deployable`, `foundation_netio::simple_http`,
  `ProviderClient<S, R>` and `foundation_deployment::providers::cloudflare`.
  `CloudflareWorker::deploy` reads the script into `_script` and never uploads it.
- **Decide first:** `rg -n ewe_deployables --glob '!crates/ewe_deployables/**'`. If nothing uses
  it and the per-provider deployment crates cover it, delete the crate (one commit, say why in
  the PR). Otherwise port it to the async `Deployable` / `StateStore`, add it to the workspace,
  and upload the script through the generated Workers upload type (rule 5).
- **Test (port only):** `cloudflare_worker_deploy_uploads_script` against a mock API (the request
  body has the script bytes, streamed).

## E3. The Cloudflare crate is too large (task #28)

- **Fix:** split the generated Cloudflare groups into crates per group, generated by the same
  generator command (fix the generator, rule 5); `foundation_deployment_cloudflare` re-exports
  them behind features so callers do not change. Coordinate with feature 17 E2 (shared R2/D1
  types crate): the types crate from E2 becomes one of the group crates.
- **Verify:** `cargo build -p foundation_deployment_cloudflare` time and size before and after,
  in the PR body; every caller builds unchanged.

## E4. Wasm runtime tests never run in CI (both backlog entries)

- **Problem:** the CI wasm step is `cargo check --target wasm32-unknown-unknown` on libraries
  only. `foundation_core/integration/wasm_tests` (outside the root workspace),
  `tests/valtron/wasm_js_yield_integration.rs` and the other `wasm_bindgen_test` suites are not
  even compiled.
- **Fix:** a CI job that (1) runs `cargo check --tests --target wasm32-unknown-unknown` for each
  crate with wasm tests and for `integration/wasm_tests`, and (2) runs
  `mise run test:wasm-testbed:deno` and `mise run test:wasm-bindgen:deno` (embedded Deno; no
  browser). Add it to `ci/packages.toml` / the workflow the way other jobs are added.
- **Verify:** `python3 scripts/ci/ci.py plan` lists the job; it passes in CI; a deliberately
  failing wasm test (local only, not committed) makes it fail.

## E5. `wasm-testbed` warns on `Command::Bindgen(args)`

- **Where:** `foundation_testbed/src/bin/wasm-testbed.rs:37`: `args` is unused without the
  `wasm-bindgen-test` feature.
- **Fix:** gate the binding with the same `cfg` as its use.
- **Verify:** `cargo check -p foundation_testbed --no-default-features --features wasm-embedded-js 2>&1 | rg warning` is empty.

## E6. A wasm mise task installs every tool in `mise.toml`

- **Fix:** a separate mise environment (for example `mise.wasm.toml` with `MISE_ENV=wasm`) that
  pins only deno and wasm-bindgen; the wasm tasks use it. E4's CI job uses it too.
- **Verify:** in a clean `MISE_DATA_DIR`, `MISE_ENV=wasm mise run test:wasm-bindgen:deno`
  installs only those two tools (list the install log in the PR).

## E7. `foundation_keychain` wasm warnings (§21)

- **Fix:** move `rmpv` to the native target section of `Cargo.toml`; drop the unused
  `notifications::self` import (`src/server/signalr_do.rs:29`) and the unneeded `mut resp` (line 74).

## E8. `foundation_deployment_cloudflare` wasm warning (§21)

- **Fix:** drop the unused `worker::Error` import (`src/workers/durable_object.rs:24`).
- **Verify (E7, E8):**
  `cargo check --target wasm32-unknown-unknown -p foundation_keychain -p foundation_deployment_cloudflare 2>&1 | rg warning` is empty.

## Verification (run exactly)

```bash
export CARGO_PROFILE_DEV_DEBUG=0 CARGO_INCREMENTAL=0
python3 scripts/ci/ci.py plan
for c in foundation_core foundation_testbed foundation_keychain foundation_deployment_cloudflare; do
  python3 scripts/ci/ci.py run $c --profile dev || exit 1
done
MISE_ENV=wasm mise run test:wasm-testbed:deno
MISE_ENV=wasm mise run test:wasm-bindgen:deno
cargo check --workspace --all-targets --profile dev
```
