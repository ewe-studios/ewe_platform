# Architecture Decisions

Tracked decisions for spec-39 (foundation-wasm-ui). Each decision is resolved — no longer a TODO.

## 001 — html! macro: pure Rust, no template syntax

**Date:** 2026-06-08  
**Status:** Resolved

### Decision

**Two-macro idea discarded.** `html_template!` provides no value beyond what `html!` already delivers — `html!` already produces compile-time-parsed structs with slot descriptors for partial updates, and avoids all runtime parsing. The original lit-inspired distinction (cache template vs resolve every time) collapses because both sides end up as the same thing: a compile-time struct with runtime value substitution.

Single macro:

1. **`html!`** — Compile-time parsed via `foundation_html`'s parser. Produces an `Html` struct representing the DOM tree with `Part` descriptors for dynamic `{}` slots. At runtime, constructs the resolved tree by swapping values into slots — zero runtime string parsing, no template language syntax.

### Runtime struct: `Html`

A new lightweight `Html` struct in `foundation_wasm_ui` — **not** reusing `foundation_html`'s `Fragment`:

- `foundation_html`'s `Fragment` is arena-allocated with `before`/`after` circular positioning, `SharedEncoding`, `FragmentPool` — over-engineered for client-side use
- The `Html` struct is a simple tree: `tag`, `attributes`, `children`, `text` + `Part` metadata (dynamic slot positions + types)
- `html!` compiles via `foundation_html`'s parser (reusing tag recognition, self-closing rules, attribute parsing), but produces an `Html` at runtime
- `Html` serializes to: Arrow batches (columnar DOM ops), JSON (signal patches), HTML string (SSR)

### `html!` mechanics

- `{}` delimits a Rust expression that evaluates to anything `IntoHtml`:
  - `Html` (single fragment)
  - `Vec<Html>` (multiple fragments)
  - `impl Iterator<Item = Html>` (lazy/deferred fragments)
- Loops, conditionals, and control flow are **plain Rust**:
  ```rust
  let items: Vec<_> = users.iter().map(|u| {
      html! { <li>{u.name}</li> }
  }).collect();

  html! {
      <div>
          {items}
      </div>
  }
  ```
- Macro uses `TokenTree::Group` for brace balancing — no Rust parser needed
- Nested `html!` calls inside `{}` are naturally supported

### What this replaces

- Discards `@for`, `@if`, `on:click=`, `.value:bind=`, `...{spread}`, `x-directive` template syntax entirely
- Discards `html_template!` — no value beyond what `html!` already delivers
- Replaces old_features/03-html-templates's PartType enum and two-macro approach

### Tradeoffs accepted

- Users pre-compute complex expressions outside the macro (standard Rust pattern)
- Control flow (loops, conditionals) is plain Rust, not template directives
- Part descriptors are generated by `html!`'s compile-time parsing, no separate template system
