# 13 — `#[wasm_app]` entrypoint and `foundation_wasmtime`

**Date:** 2026-07-17
**Status:** Resolved

## Decision

`#[wasm_app]` marks a function that runs as WASM inside a wasmtime runtime
embedded in the native shell. The `#[platform_bin]` source parser discovers it,
compiles the WASM, generates a wrapper module in `src/generated/`, and the
user wires it into the session via `foundation_wasmtime`'s builder pattern.
The session registry (`register_wasm_app` / `get_wasm_app`) lets routes
automatically resolve to the wasmtime-hosted app.

This was extracted from [decision 04](04-deployment-surfaces.md) — deployment
surfaces describe WHERE code runs; this decision describes HOW `#[wasm_app]`
code is built, loaded, and wired into the session.

## The build.rs pipeline

The user's crate includes `foundation_platform` as a dependency. The platform
provides a `build.rs` generator function. The user's `build.rs` is a one-liner:

```rust
// build.rs
fn main() {
    foundation_platform::generate_platform_code();
}
```

`generate_platform_code()` does everything:

1. Scans `src/` for all platform annotations (`#[platform_bin]`, `#[wasm_app]`,
   `#[platform_worker]`, `#[platform_service]`).
2. For `#[wasm_app]` functions: generates `src/bin/{name}.rs`, compiles to
   wasmtime-compatible WASM, places the `.wasm` in `shell_wasm/`.
3. Generates `src/generated/` wrapper modules for each `#[wasm_app]`.
4. For `#[platform_worker]` / `#[platform_service]`: generates native stubs.
5. Triggers the existing `WasmBundleGenerator` for any web-side annotations
   (`#[wasm_bin]`, `#[wasm_worker]`, `#[wasm_service`)).

The user NEVER runs a source parser manually. `cargo build` triggers
`build.rs`, which calls the platform generator, which produces all generated
code. The build script is simple and always the same — `foundation_platform`
owns the complexity.

### New project template

New projects start from a template in `artefacts/temples/templates/`. The
template provides:

```
my-app/
  ├── build.rs                ← foundation_platform::generate_platform_code();
  ├── Cargo.toml              ← depends on foundation_platform, foundation_wasmtime
  ├── src/
  │   ├── main.rs             ← #[platform_bin] fn main(session)
  │   ├── generated/          ← initially empty (populated by first build)
  │   └── app/
  │       └── mod.rs           ← placeholder for #[wasm_app] functions
  ├── src/bin/                ← initially empty (populated by first build)
  └── shell_wasm/             ← initially empty (populated by first build)
```

The user runs `cargo generate` (or the platform's CLI) with the template,
writes their `#[wasm_app]` functions in `src/app/`, and `cargo build`
handles the rest. The template ensures every new project has the correct
`build.rs`, dependency set, and directory structure from day one.

## Code generation: src/bin and src/generated

The `#[platform_bin]` source parser discovers `#[wasm_app]` functions in the
user's crate. For each function, it produces two artifacts:

### 1. src/bin/{name}.rs — the WASM binary entrypoint

```rust
// Generated: src/bin/business_logic.rs
// Compiled to wasm32-wasip1 (or equivalent wasmtime-compatible target).
// This is the entrypoint that runs inside wasmtime.

#[wasm_app]
fn business_logic(session: PlatformSession) {
    // The user's original function body.
    // The session handle is bridged from the host via wasmtime imports.
    // The WASM exports functions; the host (native shell) calls them.
}
```

The generated `src/bin/*.rs` wraps the original function with the correct
`#[wasm_app]` attribute so it compiles as a standalone WASM binary. The
compiled `.wasm` lands in `shell_wasm/{name}.wasm`.

### 2. src/generated/{name}.rs — the host-side wrapper

Generated in `src/generated/` (see directory structure below). This is
compiled natively as part of the host crate. It provides a `builder()`
function that loads the WASM bytes via `PackageDirectorate` and returns a
pre-configured `WasmtimeBuilder`.

## Generated directory structure

```
User's crate/
  ├── build.rs                ← foundation_platform::generate_platform_code();
  │
  ├── src/
  │   ├── main.rs             ← contains #[platform_bin]
  │   ├── generated/          ← auto-generated by build.rs
  │   │   ├── mod.rs          ← pub mod business_logic;
  │   │   └── business_logic.rs
  │   └── app/
  │       ├── mod.rs
  │       └── logic.rs        ← contains #[wasm_app] fn business_logic
  │
  ├── src/bin/                ← auto-generated by build.rs
  │   └── business_logic.rs   ← wasmtime entrypoint, compiled to wasm32-wasip1
  │
  ├── shell_wasm/             ← compiled .wasm artifacts (bundled via EmbeddableDirectory)
  │   └── business_logic.wasm
  │
  └── webview_assets/         ← #[wasm_bin] / worker / service bundles
      └── ...
```

The `src/generated/` directory is checked into git so CI and other developers
don't need to run the build to see the generated code. `build.rs` regenerates
it on every build to keep it in sync.

### Generated `src/generated/business_logic.rs`

```rust
// Auto-generated by foundation_platform::generate_platform_code().
// Wraps the compiled business_logic.wasm in a foundation_wasmtime builder.

use foundation_packager::PackageDirectorate;
use foundation_wasmtime::WasmtimeBuilder;

/// Returns a pre-configured builder for the business_logic WASM app.
/// The WASM bytes are loaded via PackageDirectorate — embedded in the
/// binary in release builds, read from disk in debug mode.
pub fn builder() -> WasmtimeBuilder {
    let wasm_bytes = <ShellWasmAssets as Default>::default()
        .get_file("business_logic.wasm")
        .expect("business_logic.wasm not found in shell wasm assets");

    WasmtimeBuilder::new(wasm_bytes)
}

#[derive(Default)]
struct ShellWasmAssets;
impl foundation_packager::EmbeddableDirectory for ShellWasmAssets {
    // In release: reads from embedded bytes
    // In debug: reads from shell_wasm/ on disk
}
```

### How PackageDirectorate hooks in

| Build mode | How `get_file("business_logic.wasm")` resolves |
|---|---|
| **Debug** | Reads from the filesystem: `shell_wasm/business_logic.wasm`. No recompile after WASM changes — just rebuild the `.wasm` and restart. |
| **Release** | `EmbeddableDirectory` bakes the bytes into the binary at compile time. `get_file()` returns from static memory. No filesystem reads. |

The pattern is the same one used by `foundation_packager` for templates and
static assets — `PackageDirectorate` abstracts over embed-vs-filesystem.

## `foundation_wasmtime` crate

A new crate that owns the wasmtime surface. It provides:

```rust
// foundation_wasmtime::WasmtimeBuilder (conceptual)
impl WasmtimeBuilder {
    /// Create a builder with WASM bytes loaded.
    pub fn new(wasm_bytes: Vec<u8>) -> Self { ... }

    /// Add a custom import module. The session calls .build(&session)
    /// which auto-wires "platform" and "session" imports.
    pub fn with_import(name: &str, exports: Exports) -> &mut Self { ... }

    /// Finalize: instantiate the wasmtime Engine, Linker, and Module.
    /// The session wires its standard imports ("platform", session handle, etc.)
    /// when .build() is called.
    pub fn build(self, session: &PlatformSession) -> Result<WasmtimeInstance> { ... }
}

/// A running wasmtime instance. The session can call its exported functions.
pub struct WasmtimeInstance {
    store: wasmtime::Store<PlatformSession>,
    instance: wasmtime::Instance,
}
```

### Key design choices

- **The builder, not the session, owns wasmtime setup.** The session provides
  standard imports when `.build(&session)` is called. Users add custom imports
  via `.with_import()` before calling `.build()`.
- **One Engine per platform.** The session creates a single `wasmtime::Engine`
  at startup. All `#[wasm_app]` instances share it. Engine creation is
  expensive; sharing it is free.
- **One Store + Instance per app.** Each `#[wasm_app]` gets its own
  `wasmtime::Store` and `Instance`. Host functions in the Store can access the
  `PlatformSession` via `Store::data()`.

## Session registry: register_wasm_app / get_wasm_app

```rust
// In #[platform_bin], the user wires it up:
fn main(session: PlatformSession) {
    // Get the pre-configured builder from the generated module.
    // The builder already has WASM bytes loaded (via PackageDirectorate).
    let instance = generated::business_logic::builder()
        .with_import("db", session.db().exported_functions())
        .with_import("custom", my_custom_imports())
        .build(&session)?;

    // Register with the session.
    session.register_wasm_app("business_logic", instance);

    // Any code can retrieve it later:
    let app = session.get_wasm_app("business_logic");
    app.call("handle_request", &payload);
}
```

The registry is a `HashMap<String, WasmtimeInstance>` on the session. Users
can register multiple `#[wasm_app]` instances under different names.

## Auto-routing

Routes that match `/{name}/*` automatically resolve to `RouteSource::IpcShell`
and dispatch to the registered `#[wasm_app]` instance:

```
Browser navigates to /business_logic/dashboard
  → session route handler runs
  → no explicit handler matches → auto-route kicks in
  → "business_logic" matches registered wasmtime app name
  → session calls business_logic instance, passes the route
  → WASM in wasmtime handles the request, returns response
  → session delivers response through the rendering lane
```

Users can also resolve routes explicitly:

```rust
session.route("/custom/business/*", RouteDecision::ipc_shell());
```

Auto-routing is a convenience, not a constraint. Explicit route handlers
always take priority over auto-routing.

## Three execution contexts compared

| Annotation | Where it runs | Compilation target | How it's loaded | Session access |
|---|---|---|---|---|
| `#[wasm_bin]` | WebView main thread | `wasm32-unknown-unknown` | `foundation-wasm-ui.js` instantiates in JS context | `PlatformSession` bridged from JS |
| `#[wasm_app]` | wasmtime inside native shell | `wasm32-wasip1` | `foundation_wasmtime` loads bytes, instantiates via wasmtime API | Direct — same process, `Store::data()` holds session handle |
| `#[platform_bin]` (native) | Native shell process | Native (aarch64/x86_64) | Compiled natively, linked into Tauri binary | Owns the session |

All three can coexist in the same app. The session backbone is the universal
message bus between them. A route handler dispatches to the right context
based on `RouteSource` — it doesn't know or care whether the backend is WASM
in the WebView, WASM in wasmtime, or native code.
